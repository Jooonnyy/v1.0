# 视觉方案：目标定位、颜色与色环

**状态（2026-11-16）**：PC 侧脚本已在 Windows 本机跑通（相机实时画面、图像源换算、`$V` 帧 CRC）；
**固件仍未编译、未上板，树莓派上未跑**。颜色块用合成图验过，载物盘 / 色环仍只有骨架，
真正确认要靠下面的判据逐项实测。

## 1. 现状与目标

已有的链路是**事件型**：树莓派扫二维码 → `TASK 156+123+516+231` → USART3 → STM32 → 串口屏。
它只能传"任务是什么"，传不了"东西在哪"。

目标是把同一条 USART3 升级成**状态型感知通道**：视觉节点每帧输出一个带序号、帧龄和 CRC 的目标，

```
相机 → 颜色/形状分割 → 像素→毫米（五点单应） → $V,...*CRC → USART3 → STM32 board_vision → 快照
                                                                  ↓
                                                       App 决策（选哪个目标、怎么对位）
```

分工界线：**树莓派只回答"看到什么、在哪"；STM32 只回答"这个器件现在是什么状态"；
选哪个目标、走不走、抓不抓是 App 的事。** 这条界线不守住，后面调不动。

> **2026-11-16 精简**：棋盘格内参（`calib_intrinsic.py`）和 solvePnP 外参
> （`calib_plane.py`）已从工程删除。对准是闭环，只需要"像素 ↔ 毫米"的一张单平面映射，
> 五点单应就够；那个完整标定路线从来没在实车上跑过，留着只是让人以为必须先标定。
> 现在标定只有两条：**五点单应**（要毫米坐标时）和**颜色区间**（必须现场标）。

USART3 同时跑 `TASK` 和 `$V`，所以固件侧的解析器只接纳 `$` 开头的行，其它行原样跳过，
不会干扰任务码链路。

## 2. 坐标系与平面模型

全工程统一（`Tools/vision/common.py` 顶部、`board_vision.h` 注释、本文三处必须一致）：

| 坐标系 | 定义 |
|---|---|
| 车体 | x 指向车头前方，y 指向车体左侧，z 向上；原点 = 车体中心在地面的投影；单位 mm |
| 相机 | OpenCV 惯例：x 右、y 下、z 朝前 |
| 安装角 | 相机相对车头的转角用 `common.rotate_to_body()` 补偿；`CAMERA_MOUNT_DEG` 默认 90°（本车实测） |
| 变换 | 像素 ↔ 车体毫米由 `calib_plane_h.py` 的五点单应求一次，不需要内参 |

**相机安装角必须对上**（2026-11-16 实机踩过）：`align_send.py` 按"画面正上方 = 车头"
算误差，相机实际歪了 90° 时，固件拿到的方向也歪 90°，闭环就变成绕着物料转圈——
日志特征是 `|e|` 几乎不变、角度匀速转、`ff` 被带到很大。判断和修正见
[视觉对准_ALIGN](视觉对准_ALIGN.md) §4.2。正装的相机这个值就是 0。

**为什么用单应而不是完整标定**：内参 + solvePnP 求的是相机相对车体的完整位姿，
能同时算物料台面和地面两个高度；代价是要打印棋盘格、拍 20 张、再摆一次板。
对准（ALIGN）只在一个平面上把误差收到 0，单应完全够用，五下点击就标完。
**真要区分高度**（物料台面 120 mm 与地面 0 mm）：每个高度各标一张单应文件，
或者用 TOF 测出高度后换文件。

角度不从 `minAreaRect` 直接读，而是把"中心"和"中心沿主轴外推 12 px"两点都投到平面上，
用两点连线求 atan2。这样相机怎么歪装都不影响结论，省掉一堆符号假设。

## 3. 标定：只剩两条

相机装到车上之后**不许再动**（位置、俯仰、对焦、变焦都不行）。动了就整套重标。

| 标定 | 什么时候必须做 | 脚本 | 产物 |
|---|---|---|---|
| 五点单应 | 要发 `$V` 的毫米坐标时 | `calib_plane_h.py` | `calib_plane_h.json` |
| 颜色区间 | 每次换场地/换光照都要重标 | `calib_color.py` | `colors.json` |

**不需要内参，也不需要棋盘格**。`calib_intrinsic.py` / `calib_plane.py` 已于 2026-11-16 删除。

### 3.0 采集：先拍样本图（2026-11-08 新增）

**方案是双相机**：一个专扫二维码，一个识别物料。树莓派上 USB 相机的 `/dev/videoN` 编号会随
插拔顺序变，**必须先用 udev 规则固定成 `/dev/cam_target`（物料）和 `/dev/cam_qr`（扫码）**，
之后所有脚本只认这两个名字。`--camera` 从 2026-11-08 起既接受序号也接受设备路径。

规则文件已放在 `Tools/vision/99-cams.rules`（2026-11-09 按实机输出写好）：

```bash
sudo cp Tools/vision/99-cams.rules /etc/udev/rules.d/
sudo udevadm control --reload-rules && sudo udevadm trigger
ls -l /dev/cam_target /dev/cam_qr                    # 应指向 video2 / video0
v4l2-ctl -d /dev/cam_target --list-formats-ext | head # 能列格式才是采集节点
```

实机情况（**2026-11-09 `cam_check.py` 看过画面确认**）：

| USB 口 | 型号 | 节点 | 对着哪 | 符号链接 |
|---|---|---|---|---|
| `1.3` | LRCP G720P | `/dev/video0` | **物料台** | `/dev/cam_target` |
| `1.4` | LRCP V1080P | `/dev/video2` | **二维码** | `/dev/cam_qr` |

**每台 UVC 相机在 `/dev` 下出两个节点**，`video-index0` 是真正的采集节点、
`video-index1` 是 UVC 元数据节点——后者能被 `open()`
成功打开，但 `read()` 永远不出帧。所以规则里必须带 `ATTR{index}=="0"`；漏了它，
症状是"相机能打开但黑屏/无帧"，而且不报错。`vision_node.py` 现在连续 60 次读不到帧会直接
退出并提示这一点，不再静默死循环。

> 注意物料识别用的是**720P** 那台（不是最初猜的 1080P）。代码目前请求 640×480，
> 先这样跑通闭环；要不要提到 1280×720 等第一次标定完了再定——改分辨率要重标单应。

采集样本（这一步**不需要**任何标定文件）：

```bash
python3 vision_node.py --camera /dev/cam_target \
    --save-dir samples/raw --save-every 10 --max-save 0
```

存的是**原始帧**。色环算法回归时用 `--source dir --dir samples/raw` 读回去。
文件名为 `<task>_0000.png`，换一类目标就换一次 `--task`，避免混在一起。

**没标定也能跑**：串口会照样自动打开（方便先确认线通），但不给 `--homography` 时
节点不发 `$V`——发出去也只是 0 坐标的废帧；此时终端每 0.5 s 打一条 `[detect]` 显示检出像素。
实时画面默认就开，只有 `--no-preview` 才关；不想开串口就 `--no-send`。

**用 Thonny 跑的话**：参数写在 `main.py` 开头，或直接用终端传参；
原来的 `vision_run.py` / `calib_color_run.py` 启动器已删除。

> **串口只有一个进程能持有。** `rpi_task_link.py` 与 `vision_node.py` 都是各自打开
> `/dev/serial0`，同时跑会有一个报 `Permission denied`，或者更糟——两个都"打开成功"、字节交错、
> STM32 侧 CRC 全错。正确做法是把扫码并进 `vision_node.py` 的一个线程、共用同一个 `link`。
> **这一条尚未实现。**

### 3.1 五点单应（要毫米坐标才做）

把一张已知边长的方格纸放在目标平面上，按顺序点 5 个点：①车尾右 ②车头右 ③车头左 ④车尾左
⑤车体原点（夹爪/相机光轴正下方）。点完立刻在实时画面上叠出反投的方格和原点，用卷尺比一下。

```bash
python3 calib_plane_h.py --camera 0 --square-mm 100          # 现场点击 + 自动复核
python3 calib_plane_h.py --check                             # 单独复核已标好的文件
python3 calib_plane_h.py --image shot.png --square-mm 100 \
    --points 100 400 500 410 510 120 110 115 300 260         # 无界面
```

**判据：四角残差 RMS < 3 mm，两条边长相对差 < 10%**（超了说明点歪了或纸不平）。
输出 `calib_plane_h.json`，`vision_node.py --homography calib_plane_h.json` 才发得出 `$V`。

### 3.2 颜色

```bash
python3 calib_color.py --name 3                 # 实时画面按空格冻结 → 鼠标框选 → 自动验证画面
python3 calib_color.py --image card.jpg --box 120 80 60 60 --name 3
```

输出写进 `colors.json`（同一文件会被多次调用叠加，6 个颜色跑 6 次）。
仓库里的默认区间只是"能跑起来"的起点，**比赛前必须用实物重标**。

**判据：同一颜色在 3 种光照下各标一次，三次区间的交集仍能覆盖实物**。
红色的色相跨 0，脚本会自动拆成两段区间；黑色靠"低饱和 + 低亮度"判，最容易和阴影混，
标完的验证画面（绿色轮廓）里如果黑料和阴影同时被框住，就先别用这个区间。

## 4. 协议

```text
$V,<seq>,<cls>,<x_mm>,<y_mm>,<yaw_mdeg>,<conf_permille>,<age_ms>*<crc8>\n
```

| 字段 | 含义 |
|---|---|
| `seq` | 视觉侧帧序号，逐帧 +1；STM32 用它去重和统计丢帧 |
| `cls` | 0 = 本帧无目标；1..6 颜色（与任务码一致：1红2黄3蓝4绿5黑6浅蓝）；10 载物盘；11 色环 |
| `x_mm` / `y_mm` | 车体坐标，前向 / 左向，单位 mm，量程 ±2000 |
| `yaw_mdeg` | 目标主轴与车体 x 轴夹角，逆时针为正，单位 0.001 度，量程 ±180000 |
| `conf_permille` | 置信度 0..1000 |
| `age_ms` | 视觉侧从采集到发出的耗时（帧龄），上限 2000 |
| `crc8` | CRC-8/ATM（多项式 0x07，初值 0x00），范围是 `$` 之后、`*` 之前 |

形状示例（校验值以脚本实际算出的为准）：`$V,1024,3,-42,315,1234,920,38*XX`，
无目标帧：`$V,1025,0,0,0,0,0,35*XX`。

115200 下 15 Hz × 约 45 字节 ≈ 5.4 kbps，余量充足。

### 4.1 反向：固件 → 视觉的类别指令

同一路 USART3 是双向的。每次 `ALIGN` / `TRACK` / `GRAB <cls>` 启动时，STM32 会回一行：

```text
$C,<cls>\n
```

`cls` 取值同 `$V`（1..6 颜色、10 载物盘、11 色环）；**环模式再带目标序号和转台角**：
`$C,11,<n>,<rot_deg>,<stage>`（如 `$C,11,2,132,0`），n = 第几个环，rot_deg = 转台当前角度，
stage = 0 顶部粗对 / 1 底部精对。
视觉用 `相机安装角 + 转台角` 算车体坐标，和物料跟踪同一套。树莓派上的 `align_send.py` /
`vision_node.py` 收到后就把目标类别切过去，**不用重启脚本**——这样蓝牙（UART5）或
USART1 发来的命令可以直接换颜色：`GRAB 3` 跟蓝色，`GRAB BLUE` 也是 3。

`align_send.py` 收到 **11** 会切到环检测（`detect_rings()`：CLAHE + HoughCircles + 圆心聚类），
**只报离夹爪最近的一个环**，并读环里的数字（`digit_templates/1..3.png` 模板匹配）；
`$C,11,<n>` 的 n 是期望环号（底部精对才读数字），不一致时按 `--ring-digit-check` 提示或拒绝发送。
收到 1..6 再切回颜色。`cls=10`（载物盘）`align_send.py` 仍不支持，要用 `vision_node.py --task tray`。

视觉侧只认 `$C,` 开头的行，其它下行内容忽略；没接成双向（只接了 Pi→STM32）或加了
`--no-send` 时收不到，类别就保持在命令行给的 `--cls` / `--want`。

单独验证这条下行：树莓派跑 `align_send.py --link-test`（只读不写），STM32 发 `HINT 3`，
应看到 `RX b'$C,3\n'`；`VER` 可确认板上固件是不是带 `$C` 的那版。

## 5. 固件侧

| 项 | 位置 |
|---|---|
| 解析与快照 | `BSP/Inc/board_vision.h`、`BSP/Src/board_vision.c` |
| 调用点 | `App/Src/vehicle_app.c` 的 `VehicleApp_Begin()`（`Vision_Init()`）与 `VehicleApp_Poll()`（`Vision_Poll()`） |
| 命令 | USART1 发 `V`，打印一帧快照 + 统计 |

`Vision_Poll()` 只在主循环里跑，中断仍只往环形缓冲塞字节（符合 AGENTS.md 第 6 节）。
它**不发送任何数据**，所以不会在步进脉冲期间阻塞。

`V` 的输出形状：

```
VIS ok=.. bad=.. rep=.. gap=.. ovf=.. drp=..
TGT cls=3 x=-42 mm y=315 mm yaw=1234 mdeg conf=920 age=38 ms seq=1024 stale=0
```

- `bad` 一直涨：CRC 或量程不过，先看 Pi 侧和波特率；
- `rep` 涨而 `ok` 不涨：视觉卡住了还在重发同一条（固件故意不刷新时间戳）；
- `gap` 涨：丢帧，看串口线或 Pi 侧频率；`ovf` 涨：一帧超过 64 字节被判超长；
- `drp`：USART3 环形缓冲溢出（主循环太久不调 `Vision_Poll()`）；
- `stale=1`：超过 `VD_STALE_MS`（200 ms）没更新，此时 App 必须退回里程计，不能拿它闭环。

## 6. 四个阶段与判据

| 阶段 | 做什么 | 判据 |
|---|---|---|
| ① 骨架 + 标定 | 本文 3.1 + `vision_node.py --source image` 走通换算 | 五点单应残差 < 3 mm；卷尺比对 100 mm 处误差 < 5 mm |
| ② 载物盘 / 物料定位 | `--task tray` 取最大凸四边形；`--task color` 按颜色出块并判形状 | 静止摆放 10 个位置，`x_mm/y_mm` 与卷尺差 < 5 mm；形状判别 20 次全对 |
| ③ 颜色 + 抓取 | 用任务码的 `--want` 只送目标色；抓取前/后各看一次做校验 | 6 色 × 3 光照 × 50 帧混淆矩阵 > 98%；浅蓝/蓝不混；漏检/误检 < 2% |
| ④ 色环 | `--task ring`，颜色掩膜 + 轮廓层级找环，算内外径比 | 环心 < 3 mm、内径 < 5%、漏检 < 5% |

闭环形态（阶段②之后才谈）：视觉给"目标相对位姿" → 换算成底盘目标点 → 交给现有里程计闭环跑过去
→ 最后 15 cm 切纯视觉微调。**不要拿 10 Hz 的视觉直接驱电机**：0.6 m/s 下 100 ms 延迟就是 60 mm。

### 6.1 形状过滤（2026-11-09 新增 `--shape`）

场景里有别的物体和物料同色时，只靠 HSV 会产生误检。`--shape any|circle|rect` 在
`pick_candidate()` 之前按几何形状过滤一层。

判据不再用 `4πA/P²`（正方形 0.785，和圆的 1.0 挤在一起，阈值定在哪都容易错判），
改用**面积 / 外接几何体面积**：

| 形状 | 外接圆填充率 | 外接矩形填充率 |
|---|---|---|
| 正圆 | ≈ 1.00 | ≈ 0.79 |
| 正方形 | ≈ 0.64 | ≈ 1.00 |
| 正三角形 | ≈ 0.41 | ≈ 0.50 |

圆和方的分离度从 0.2 拉到 0.36，阈值好定得多。另外加了**凸包填充率 < 0.85 直接丢弃**：
碎片化的掩膜（反光、边缘碎块）质心没有意义，这类候选正是背景杂物误检的主要来源。

`--show-all` 模式的框边会标 `cf` 值（外接圆填充率），拿它现场调阈值：
圆柱物料应该稳定在 0.9 以上，形状不规则的背景杂物会明显偏低。

**逐类形状约束**：`colors.json` 的每个类可以额外写三个可选字段，只对这一类生效，
不影响别的颜色：

| 字段 | 作用 |
|---|---|
| `min_circle_fill` | 外接圆填充率下限，压掉阴影、色块边缘这类非目标形状 |
| `min_solidity` | 凸包填充率下限，压掉碎片化掩膜 |
| `min_area_px` | 覆盖全局 `--min-area-px` |

黑色必须用这个：它只能靠低亮度判断，而阴影的亮度和它几乎一样，纯 HSV 一定会把
阴影选进来（现象是黑料的标签落在别的物料的暗部上）。加 `min_circle_fill` 之后，
月牙形的阴影过不了、圆形黑料能过。

`calib_color.py` 重标时会**保留**这三个字段，只更新颜色区间。

### 6.2 暗色目标（黑色）的独立检测路径

黑色不能走 HSV。原因是黑料的 V 和它旁边阴影的 V 是同一个量级，而且补光在物料顶部
打出高光后，黑料中心的 V 反而可能**高于**旁边暗部——绝对阈值怎么调都是"压掉阴影就
连黑料一起压掉"。实测现象就是 `5` 的框落在别的物料的暗部上，真黑料没框住。

`colors.json` 里给这一类写 `"mode": "dark"` 就切换到独立路径（`build_dark_mask()`），
判据变成三条**相对**判断：

| 判据 | 字段 | 默认 | 含义 |
|---|---|---|---|
| 比局部背景暗 | `dark_ratio` | 0.22 | 局部背景在 1/8 分辨率上高斯估计再放大（sigma = 小图宽×0.16），补光不均也自适应；640×480 由 700 ms 降到 12 ms |
| 绝对亮度上限 | `max_v` | 170 | 防止把中灰背景也当黑 |
| 饱和度上限 | `max_s` | 140 | 黑料偏灰，不该像彩色那样鲜艳 |
| **不贴着彩色物体** | `shadow_guard_px` | 28 | **关键**：阴影永远紧贴它所属的物体，孤立黑料不会 |

第四条是真正把黑料和阴影片开的依据。前三条决定"哪里暗"，第四条决定"这个暗区像不像阴影"。

**性能（2026-11-16 实测，PC）**：`detect_blobs` 全六色 640×480 **13 ms/帧**、320×240 **3.5 ms**；
其中黑色 dark 路径是大头（12 ms），彩色掩膜约 0.5 ms/类。之前的写法对全图做 σ≈102 的高斯，
一帧要 716 ms，这才是"全色检测帧率低"的根因。阴影禁区现在直接复用已建好的彩色掩膜，不再重算一遍。

调参顺序：先跑 `--debug-mask masks`，看生成的 `*_cls5_black_dark.png`。
掩膜里同时框住了黑料和阴影 ⇒ 调大 `shadow_guard_px`；
掩膜几乎全黑 ⇒ `dark_ratio` 调小或 `max_v` 调大；
掩膜里黑料只是一小块碎斑 ⇒ 是补光高光把物料啃断了，加柔光罩。

## 8. 脚本速查：每个都能在电脑上看到实时画面

2026-11-16 统一：**相机默认 `0`（PC 上就有画面），窗口默认开，`--no-preview` 才关**；
**串口发送默认开**：先试 `/dev/serial0`，再按 CH340/CP210x/FTDI/STM32-VCP 的优先级扫 USB 串口，
打开后会打印实际用的口名。接错了用 `--port COM7` / `--port /dev/serial0` 指定，
不想发加 `--no-send`。没有图形界面（纯 ssh）时窗口自动降级成只打印，不会崩。
下表命令都在 `Tools/vision/` 目录下执行；`colors.json` / `calib_plane_h.json` 按脚本目录解析，
在仓库根敲 `python Tools/vision/vision_node.py` 也不会找不到文件。

| 想干什么 | 命令 | 看到什么 |
|---|---|---|
| 看相机、看识别 | `python vision_node.py` | 绿色框 = 选中的目标，左上角 fps |
| 双相机 + 扫码 | `python main.py --camera /dev/cam_target --qr-camera /dev/cam_qr` | 收到 `SCAN` 后扫二维码、上屏、打印两批顺序 |
| 查颜色串不串 | `python vision_node.py --show-all` | 每个候选一个颜色 + 底部计数 |
| 查某个颜色为什么检不出 | `python vision_node.py --debug-mask masks` | 掩膜图落在 `masks/` |
| 对准发帧 | `python align_send.py --cls 3` | 红点 = 目标，十字 = 夹爪；自动开串口发 `$V` |
| 标五点单应 | `python calib_plane_h.py --square-mm 100` | 点击处标号，标完叠出反投方格 |
| 复核单应 | `python calib_plane_h.py --check` | 绿框 + 红十字 + 中心毫米坐标 |
| 标颜色 | `python calib_color.py --name 3` | 空格冻结 → 框选 → 验证轮廓 |
| 认相机 | `python cam_check.py` | A/B 两路并排，标着分辨率 |
| 调曝光 | `python cam_tune.py` | 滑条 + 过曝百分比 + 鼠标处 HSV |

树莓派上把 `--camera 0` 换成 `--camera /dev/cam_target`（装过 udev 规则之后）。

## 9. 排查表

| 现象 | 先查什么 |
|---|---|
| `bad` 一直涨 | 波特率是否 115200、Pi 的 `/dev/serial0` 是否真的是 `ttyAMA0`（`disable-bt`）、CRC 大小写 |
| 识别到了但 `x/y` 明显偏 | `calib_plane_h.json` 重新标一次；相机是否被碰过 |
| 颜色一会儿有一会儿没 | 相机自动曝光/白平衡是否没锁（`common.open_camera` 默认锁）、有没有补光 |
| 黑色块被识别成大片阴影 | `colors.json` 里 class 5 的 S/V 上限放宽前先看掩膜预览 |
| 色环找不到内外圈 | ROI 太小/太远；先把 `--min-area-px` 降下来，或先定位载物盘再裁 ROI |
| `stale=1` 频繁 | Pi 侧帧率不够（Pi 4B 全图 HSV 低于 10 Hz 就降分辨率到 640×480） |
| PC 上打不开相机 | 先试 `--camera 0` / `--camera 1`；关掉占用相机的浏览器/会议软件 |
