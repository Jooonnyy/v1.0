## 一、硬件规格

| 项 | 值 | 来源 |
|---|---|---|
| 电机 | **JGB37-520**，有刷直流 + 霍尔编码器，12V | 用户提供 |
| 编码器 | 单相 **11 线**，AB 相，四倍频 → 电机轴每转 **44** 计数 | 用户提供 |
| 减速比 | **1:30**（由"12V 333 rpm"反推：电机轴 ~10000 rpm ÷ 30 = 333） | 推算，**请对铭牌复核** |
| 轮子 | 直径 **70 mm** | 2026-10-27 卡尺实测（此前按标称 75 mm） |
| 每轮转计数 | 44 × 30 = **1320 counts/rev** | 计算 |
| 每计数 | **0.1666 mm** | 计算 |
| 最高轮速（空载） | **1.31 m/s**（333 rpm） | 计算 |
| 最高计数率 | **7326 counts/s** | 计算 |
| 速度常数 Kv | 27.8 rpm/V（做前馈用） | 计算 |
| 驱动 | TB6612FNG ×2：MOTOR_A/B 在 U2，MOTOR_C/D 在 U3 | `PINMAP.md` |
| 编码器通道 | A=TIM2(PA0/PA1)、B=TIM3(PB4/PB5)、C=TIM4(PD12/PD13)、D=EXTI(PD8/PD9) | `PINMAP.md` |

> **减速比必须核实。** 如果 44 其实是"**轮子**每转"（直驱无减速箱），
> 每计数就变成 5.355 mm，10 ms 窗口在 0.5 m/s 只能数到 0.93 个计数
> —— M 法直接失效，必须换成 M/T 法。铭牌上一般直接印着 `1:30`。

### 为什么 1:30 很关键：测速分辨率

M 法（固定 10 ms 窗口数计数）的量化误差 = 1 ÷ 窗口内计数：

| 车速 | counts/s | 10 ms 窗口计数 | 量化误差 |
|---:|---:|---:|---:|
| 0.1 m/s | 560 | 5.6 | 18% |
| 0.2 m/s | 1120 | 11.2 | 9% |
| 0.5 m/s | 2801 | 28.0 | **4%** |
| 1.0 m/s | 5602 | 56.0 | 2% |
| 1.3 m/s | 7283 | 72.8 | 1% |

正常行驶区间（0.2~1.3 m/s）误差 1~9%，配一个一阶低通足够。
**低于 0.1 m/s 误差才明显变大**，但那不是正常行驶速度，本阶段不处理。

机械时间常数（70 mm 轮 + 1:30 减速）约 30~80 ms，所以
**10 ms / 100 Hz 的控制周期绰绰有余，不需要 1 kHz。**

## 三、修掉的 bug：`Encoder_Read()` 有副作用

**这是本次最实质的修复。**

旧实现（`board_motion.c`）一个 API 有三种语义：

```c
case ENCODER_A: return (int32_t)TIM2->CNT;          /* 原始值，不累积 */
case ENCODER_B:
  total_b_counts += (int16_t)(now - last_b_counts); /* ← 每次调用都吃掉增量 */
  last_b_counts = now;
  return total_b_counts;
case ENCODER_D: return encoder_d_counts;            /* EXTI 累计值 */
```

TIM3/TIM4 是 16 位计数器，必须靠"上次原始值"扩展成 32 位，而这个状态就藏在读函数里。
后果：**控制中断和主循环遥测各调一次 `Encoder_Read(ENCODER_B)`，
两边就会互相抢走对方的增量**，读数都错且错得没有规律 —— 波形看着像"能跑但偶尔跳"，
极难排查，很容易被误判成 PID 没调好。

**修复方式**：把"扩展"和"读取"彻底分开

- `Encoder_SampleCounts()` —— **全局唯一的更新点**，只在 100 Hz tick 里调用一次
- `Encoder_ReadCounts(id)` —— **无副作用**，任何上下文、调多少次，返回值和状态都不变

因为对齐的 32 位读写是单指令，所以不需要临界区。

## 四、VOFA+ 使用

| 项 | 设置 |
|---|---|
| 串口 | USART1（PA9=TX / PA10=RX），**115200 8N1** |
| 协议 | **FireWater** |
| 通道数 | **9** |
| 通道含义 | `cA,cB,cC,cD,sA,sB,sC,sD,t` |
| `cX` | 该轮累计计数（已按 `ENCODER_x_SIGN` 归一化，正数 = 前进方向） |
| `sX` | 该轮转速，单位 counts/s；**× 0.1785 = mm/s** |
| `t` | tick 计数，**诊断用**：不动 = TIM7 中断没进来 |

`t` 这个通道是专门用来分辨"读数全是 0"的两种原因的：

| 现象 | 结论 |
|---|---|
| `t` 在涨，但某路 `cX` 不动 | 测速在跑，是**那一路编码器**没接好 / 没供电 / 引脚没通 |
| `t` 一直不动，所有 `cX` 也是 0 | **TIM7 中断没进来**（板子没跑到这里，或时钟没配对） |
| `t` 停在某个值不动 | 程序卡住了（进了 `Error_Handler` 或 HardFault） |

发送频率 50 Hz（`ENCODER_SMOKE_TX_HZ`），一行约 55 字节 ≈ 2.8 kB/s（占 115200 的 24%）。
要调到 100 Hz 就把这个宏改成 `100U`。

**命令从 VOFA+ 自己的发送框发** —— 不要另外开串口助手，
一个 COM 口只能被一个程序占用。

> **无线调参（2026-10-02 起可用）**：原 `encoder_smoke.c` 参数区里的
> `ENCODER_SMOKE_TELEMETRY_PORT` 改成 `SERIAL_BT`，遥测就走车上的 HC-05（USART2 / PA2/PA3），
> 电脑端用另一块 HC-05 + USB-TTL 收波形，**不用再拖一根线跟着车跑**。
> 人读文本仍留在有线 USART1（`ENCODER_SMOKE_TEXT_PORT`），命令两个口都收。
> （**2026-10-27 该 Target 已删除**；等价开关由 `wheel_smoke.c` 的遥测/文本端口参数承担，
> 具体宏名见该文件参数区。）
> 模块配置与接线见 `Docs/HC05无线串口.md`。

| 命令 | 作用 |
|---|---|
| `M <a\|b\|c\|d> <permille>` | 开环驱动某一路，`-1000..1000`（台架限幅到 ±500） |
| `STOP` | 全部停 + 两片 TB6612 进待机 |
| `Z` | 4 路计数清零 |
| `S` | 立刻打印一行**人读状态**（不必接 VOFA+） |
| `T 0\|1` | 关 / 开 50 Hz 遥测流 |
| `?` | 打印命令表 |

**两种调试方式**：

- **VOFA+ 看波形**：保持 `T 1`（默认），FireWater / 9 通道。
- **串口助手看数字**：先发 `T 0`（否则 50 Hz 会把屏幕刷爆），然后按需发 `S`：

  ```
  cA=0 cB=0 cC=0 cD=0 | sA=0 sB=0 sC=0 sD=0 | t=1234 | telemetry=off
  ```

  手转轮子的同时连发几次 `S`，就能看出哪一路在动、方向对不对、`t` 有没有在涨。

> ⚠ 本固件在 USART1 上**只发数字行**，调试文字只在开机和收到命令时发。
> 如果遥测流里混进文字，VOFA+ 会出现毛刺。这条已写进 `AGENTS.md` 第 6 节。

## 五、上板验证步骤（阶段 1）

1. **先把车架空**（轮子离地）。
2. **确认编码器供电** —— 建议给霍尔编码器供 **3.3V**，输出就是 3.3V 电平，
   怎么接都不会错。若必须 5V，先逐个确认引脚 5V 容忍。
3. 烧 `Bench_Tests.uvprojx` 的 **`ENCODER`** Target（`Bench_Tests\ENCODER\ENCODER.hex`）。
4. 开 VOFA+（FireWater / **9 通道** / 115200）：应立刻看到 8 条速度线在动、第 9 条 `t` 单调增长。
   （只用串口助手也行：发 `T 0` 关掉遥测，再用 `S` 按需看一行状态。）
5. **手转其中一个轮子**，看对应通道：

| 现象 | 结论 | 动作 |
|---|---|---|
| 正转时 `cX` 增大 | 方向对 | 不用改 |
| 正转时 `cX` 减小 | 方向反 | 把 `board_encoder.h` 里对应的 `ENCODER_x_SIGN` 改成 `-1` |
| `sX` 有明显噪声/台阶 | 正常（量化） | 加大 `ENCODER_SPEED_FILTER_DIV` 或把 tick 保持在 100 Hz |
| `sX` 恒为 0，`cX` 也不动 | 该路没接好/没供电 | 量编码器 A/B 波形与供电 |
| `cX` 完全不动但其他路正常 | 该路引脚或定时器问题 | 对照 `PINMAP.md` 量通 |

6. **核对一圈的计数**：把轮子**手转整 10 圈**，`cX` 的增量应当是
   1320 × 10 = **13200**（正负取决于方向）。偏差大说明 CPR 或减速比填错。
7. 发 `Z` 清零，再发 `M a 300`，看 `sA` 是否跟 PWM 大致成正比、`sB/sC/sD` 是否基本不动。
8. 四路都验完，方向符号定下来，写回 `board_encoder.h`。

### 通过判据

- 4 路 `cX` 手转时有响应，方向符号已确定并写回
- 手转 10 圈 `cX` 增量 ≈ 13200（±1%）
- `M a 300` 时只有 A 路转，`sA` 稳定、无跳变
- `Encoder_Ticks()` 在涨（不涨就是 TIM7 中断没进来）

## 七、遗留问题与下一步

### 必须先确认的两件事

1. **减速比是不是 1:30**（见第一节的警告）。若不是，改 `WHEEL_COUNTS_PER_REV` 一个数即可，
   **PID 参数不受影响**（PID 用 counts/s）。
2. **TB6612 电流余量**（用户要求先不管，但记在这里）：
   TB6612FNG 单通道连续 1.2 A / 峰值 3.2 A，而 JGB37-520 12V 额定约 0.6~1.0 A、
   堵转约 2.5~5 A。四个电机同时跑（尤其原地自转）可能超限，且现在**没有电流反馈**
   （`PINMAP.md` 写明 PA2/PA3 的电流检测电路尚未证实接通）。固件侧至少要限幅 + 堵转检测。

### 已知的构建现象（非功能问题）

用 `UV4 -b Bench_Tests.uvprojx -t <Target>` 构建时，**µVision 会把全部测试源都编译**
（它自己的 `build_log.htm` 里逐条列出），尽管每个 Target 的 XML `<Groups>` 里
只挂了 1 个测试文件。链接阶段有 section GC，未用到的测试代码基本被丢弃
（例如 `Motor_C` 固件的 Code + RO-data 只有约 11.1 kB），所以**固件行为正确、体积影响很小**，
代价主要是编译时间。`Vehicle_Integrated` 没有 Tests 组，**不受影响**：
已核对它的 map 里只有 `VehicleApp_Begin`，没有任何测试入口。
